## 二、「生硬、不丝滑」的直接原因：我上一版自己加的降帧

v0.32.2 为了省 CPU，在 `timerCallback` 里加了「静置 700 ms 后每两拍才画一次」，即 30Hz → 15Hz。

**这个交易是错的。** 呼吸是**连续**的视觉（周期 2.6 s），15Hz 只有约 39 个采样/周期，眼睛能直接看出台阶；而且鼠标一进一出会在 15Hz / 30Hz 之间反复切换，节奏感更乱。省下的 3% CPU 换不回观感。

v0.32.3 把这段整个删掉，并换掉驱动方式（见第四节）。

## 三、光晕为什么贵 —— 五条路逐一量过，不是猜的

质点圆光晕一直是这份面板最大的单项开销。为了定位，把实现拆成五条路，同一进程、同一状态、同一帧数对照：

| 实现 | 质点段 | 整帧 | 说明 |
|---|---|---|---|
| 径向渐变（v0.32.1 及以前） | 1.73 ms | 3.24 ms | 每帧 10 个环带各求一次径向渐变 |
| 精灵图 + 分数坐标（**v0.32.2**） | 2.41 ms | 3.94 ms | 反而更慢 —— 上一版的失败方案 |
| 精灵图 + 吸附整数设备像素 | 1.53 ms | 3.06 ms | 只解决了一半 |
| 同上 + 图像插值质量压到 None | 1.54 ms | 3.04 ms | 无效果，此路不通 |
| **精灵图 + 吸附 + 图像 alpha 蒙版裁剪（v0.32.3）** | **1.05 ms** | **2.61 ms** | 采用 |
| （上界参照）吸附 + 完全不加 alpha | 0.68 ms | 2.17 ms | 画出来是错的，只用来量还有多少空间 |

两处成因：

**① 贴图坐标没对齐。** 圆心是几何表算出来的浮点数（`x = 71.2531…`），乘上设备缩放后必然落在半个像素上。CG 的 `CGContextDrawImage` 在目标矩形带分数偏移时必须重采样；整数对齐的 1:1 贴图走的是接近 memcpy 的路 —— 底图 4.1 Mpx 只要 0.43 ms（≈ 9.5 Gpx/s），而分数坐标的精灵图只有约 136 Mpx/s，**差约 70 倍**。
做法：先抵消外层的 `scale(ds)`，再平移到 `roundToInt((c.x - ro) * ds)`。复合之后设备变换 = 平移(整数)、标度恰好 1。

**② `setOpacity` 的 alpha 混合才是大头。** 吸附后仍然 1.53 ms；把 alpha 去掉（只作测量用）掉到 0.68 ms —— **0.85 ms 花在 `CGContextSetAlpha` 的逐像素混合上**。
做法：改用图像 alpha 当蒙版裁剪再填纯色（JUCE 的 `drawImageTransformed(..., fillAlphaChannelWithCurrentBrush = true)`，内部走 `clipToImageAlpha` + `fillAll()`），绕开上下文 alpha。数学上两者都是「颜色 × 精灵 alpha × peak」。

**顺带证伪一条**：曾怀疑 JUCE 默认的 `kCGInterpolationMedium` 把 1:1 贴图也拖进重采样，实测压到 `None` 后 1.53 → 1.54 ms，**无效果**。

### 逐像素对照（可复现）

`TRANE_GLOW=grad` 可以随时切回老路出图对照。`--state demo` 全幅 2880×1440：

| 对照 | 最大差 | 差 >1 的像素 | 差 >8 的像素 |
|---|---|---|---|
| grad vs 默认（mask） | **7/255** | 12 833（0.31%） | **0** |

差异全部来自吸附把光晕的硬内边缘挪了不到半个设备像素，集中在环带边缘。放大 3 倍并排看（`/tmp/glow_zoom.png` 同法可复现）：两张图肉眼完全一致，把差异放大 8 倍后只剩 1/255 量级的抖动。

## 四、动画改由显示器 vblank 驱动

`juce::Timer` 由消息线程的定时器队列驱动，误差几毫秒是常态 —— 帧间隔不齐，看起来就是"卡"。换成 `juce::VBlankAttachment`（JUCE 7 起提供，本工程用的是 9.0.2）：

- 回调跟着显示器刷新走，帧间隔天然均匀；
- 回调带一个「**这一帧什么时候被呈现**」的时间戳，用它推进呼吸相位 —— 掉帧不会让动画变慢，也不会攒出一串"补帧"（上一版用累加就会：宿主忙一下掉两帧，之后连补两帧，看着一跳一跳）；
- 回调本身很轻（记一笔 + 没到点直接返回），120Hz 屏也只在跨过 1/30 秒时才真的画一帧。

**保留 Timer 只当看门狗**：宿主 / 远程桌面不派发 vblank 时（超过 250 ms 没收到）退回定时器驱动 —— 宁可抖一点，也不能让画面冻住。

## 六、这次没做的事（诚实清单）

1. **检查器静态层没进缓存**（0.68 ms，占 26%）。它依赖行表，而行表在拖分割线时每帧都变 —— 纳入 backdrop 判据会让拖分割线时每帧重烤 4.1 Mpx 底图，反而更卡。要做得先单独拆一层"检查器静态层"并设计好失效判据，留给下一版。
2. **没有上 60Hz**。2.61 ms × 60Hz = 15.7% 单核，对一个 2.6 s 的呼吸动画来说不划算；30Hz 恒定 + vblank 对齐已经足够平滑。
3. **没上 OpenGL**。`juce::OpenGLContext` 是业界做高频动画的常见选择，但它对宿主/驱动有额外假设，且本工程"可离线验证"这条线（`panel_probe` 用和插件完全相同的绘制代码渲 PNG）会当场作废。收益不足以换掉这条线。
4. **参数同步的每帧开销没动**。`syncFromHost()` 每帧做 48 次 `apvts.getParameter`（`std::map<StringRef>` 树查找），量级在微秒，不值得改。
