### 教训：本机跑通 ≠ 全新克隆跑通

改 `run_tests.sh` 时我「优化」掉了原来的 `export PATH="...venv/bin:$PATH"`，
改成只把 ninja 路径通过 `-DCMAKE_MAKE_PROGRAM` 传给 cmake。本机有 `build/`
缓存，跑起来一切正常；**全新克隆从零构建就炸了**：

```
CMake Error: CMake was unable to find a build program corresponding to "Ninja".
ninja: build stopped: subcommand failed.
```

根因：JUCE 生成 VST3 manifest helper 时会**另起一个 cmake 子进程**配置
`external/JUCE/extras/Build/CMake/juce_v3_helper`，子进程**不继承**
`CMAKE_MAKE_PROGRAM`，只去 PATH 上找 ninja。外层只看到最后一句，
真正的错误在子进程里，非常难查。改回把 cmake / ninja 所在目录加进 PATH。

**推论：构建脚本的任何改动，都必须在 `/tmp` 里 clone 一份从零验证。**
已有 `build/` 目录会掩盖这类问题。这条已写进 `juce-vst3-plugin-dev` 技能。

另一个坑：构建的后处理会把产物拷进 `~/Library/Audio/Plug-Ins/`，沙箱会拦下
其中几个文件，命令返回非零 —— **但测试其实全过了**。判断结果要看日志里的
`passed` / `结论`，不要只看退出码。同类假失败还有 `gh auth login` 的 keychain 报错。

## UI 设计稿 v0.15 → v0.16（环形文字，同日傍晚）

小绪的规矩仍然是「先出设计稿，确认后再实操」—— **`vst/plugin/PluginEditor.cpp`

### 环形文字的两条几何规则（推出来的，不是试出来的）

1. **方向按段选。** SVG `textPath` 把字符上方向定在路径的**左手法线**上。
   屏幕坐标（y 向下）里沿 +θ 走恒为**径向朝外**，沿 −θ 走恒为**径向朝内**。
   两种朝向的倾斜角恰好差 180°，所以每段取 |φ| 小的那个 ——
   **最大倾斜恒 ≤ 90°，永远不会倒立**。φ 的公式：朝外 `atan2(cosθ, −sinθ)`、
   朝内 `atan2(−cosθ, sinθ)`。
2. **朝内那半圈路径半径 +0.5×字号。** 朝外时文字长在基线外侧、朝内时在内侧，
   不补就会上下两半错开半个字。`r_in = r_out + (帽高 − 降部)/2`。

### 每个节点的转盘要转一下

段心默认 `−90 + 180/n × (2i+1)`。**n=2 与 n=6 会正好把段摆在 3 点 / 9 点**
（那里倾斜 90°），所以搜一个旋转量让最大倾斜最小（`best_rot()`，平手取离 0 最近的）：
FREEZE → 0°、GRAIN → 60°，其余本来就是最优。实测表见脚本 `tilt_report()`。

### 半径是「往外推」出来的

名圈 33.5→46.0、值圈 35.5→…：**半径大 = 同一段角覆盖的弧更长**，
最挤的 n=6 从 29.4px 松到 31.1px（值），圆心区半径从 29.5 涨到 32。
两圈顺序也换了 —— **名圈在外、值圈在内**：刻度在外，由外往内读正好是
「SIZE 120ms」；反着放会读成「120ms SIZE」，参数名沦为补注。

## 设计稿 v0.16 → v0.17：48 个控件对账（同日傍晚，重要）

### 发现的硬伤

v0.16 定稿后去对了一遍 `PluginProcessor.cpp::createLayout()`（第 82–213 行），
**设计稿只画了 36 个控件，插件里实际声明 48 个**（+1 个 JUCE 自动加的 Bypass）。
漏的 12 个：

| 类别 | 漏掉的 |
|---|---|
| 模块开关（BoolParam） | `grain_on` `stutter_on` `comb_on` `tape_on` `sweep_on` `delay_on` |
| 旋钮 | `grain_position`（0.5） `grain_spray`（0.15） `delay_pingpong`（0） |
| 档位 | `ruin_mode`（0–1 连续 morph） `sweep_mode`（Choice LP/BP/HP） |

**教训：设计稿的参数表必须以 `createLayout()` 为唯一依据，不能凭印象列。**
现在脚本里有 `count_report()` 做对账（环位 + 开关 必须 = 48），改表就会报错。

### 两个 mode 的真实语义（读 DSP 确认，别猜）

- `ruin_mode`：**0–1 连续** morph（`Ruin.h:21` 注释 0 = Clear, 1 = Ruin；
  `out = dry*(1-mode) + ruined*mode`）。→ 当普通旋钮。
- `sweep_mode`：`AudioParameterChoice` LP/BP/HP，**原始值是序号 0/1/2**，
  `PluginProcessor.cpp:282` 用 `× 0.5` 映射成 0/0.5/1 喂给 DSP
  （`RandomSweep.h:33` 注释 0=低通 0.5=带通 1=高通）。**这个映射是对的，不是 bug。**
  → 上环时辐条长度 = 序号归一化，值直接写档位名。

### 解法：开关搬到圆的边框上

48 个控件平摊到 10 个圆，最挤的 GRAIN 有 9 个（1 开关 + 8 旋钮），
环位最多舒服地放 8 个。所以 **7 个模块开关不上环，改成圆的边框**：
关 = 淡黑细环（w1.7 op0.42），开 = **强调色红环**（w2.2 op0.95）。
点圆心区（模块名）切换。副产品是隐喻成立了 ——
**开一个亮一个，光从 Keter 逐级流到 Malkuth**。

边框亮的判据 = "这一站当前是否真的在信号里"：
有 `_on` 的看开关；`ruin` 看 `ruin_mode > 0.02`（mode=0 是纯干声）；
`space` 看 `space_mix > 0.02`；`out` 恒亮。
**注意 6 个 `_on` 默认全是 false、`freeze` 也是 false**，
所以真实初始状态是「只有 SPACE 和 OUT 亮」。设计稿用 DEMO 演示 FREEZE+GRAIN 开着。

### 半径又外推了一档（为 n=8 腾弧长）

值圈 35.5→**38.5**（fs 7.5）、名圈 46.0→**49.0**（fs 7.0）、bezel 改成贴着边界的

## 决定：不解码 MP4，构建期"烤"成帧

`asciify.mp4` = H.264 / 2920×2838 / 60fps / 5 秒 / 300 帧 / 2.36 MB。
在插件里实时解 4K H.264 要经 AVFoundation，而且**离线渲染验证会彻底失效**
（面板之所以能机器验证，就是因为输入只有 `PanelState`，没有外部状态）。

所以：`tools/build_video_frames.py` 在构建期用 ffmpeg 抽帧 → 量化 → 打包成
`assets/video/backdrop.bin`（提交进仓库，**构建插件不需要 ffmpeg**），
运行时只做「按时间取帧 → inflate → 查表」。

## 素材规格（全部实测，不是估的）

- **裁剪**：`asciify.mp4` 左右几乎对称 → **居中裁到面板比例**（`crop=1563:2838:678:0`）
  再缩到 544×988。整幅拉伸会把字符横向压扁 1.64 倍，肉眼可见失真，弃用。
- **量化到 4 档（2 bit）**，每字节 4 个像素、高位在前、行主序。
  - 连续灰阶 RGBA/PNG 100 KB/帧 → 4 级 25.7 → 2 级 16.2
  - **2 bit 打包 + zlib：9.7 KB/帧 → 75 帧 0.71 MB**（比 PNG 小 45%）
- **可读区遮罩烘进档位**（构建期，运行时零成本）：
  圆内 `r < kRingR − 1` → 档位 1；辐条区 `r < kScaleR + 6` → 档位 2；圆外 → 档位 3。
- **纸色也烘进去**：`level 0 = 纸、level 3 = 满墨`，解出来是**不透明图**。
  实测 alpha 混合 2.1M 个目标像素要 4 ms，不透明直贴只要 0.4 ms。
- 文件头（version 3，全小端）：`"TRNV"` · version · frameCount · width · height ·
  fps · levelCount · **inkRGB** · **paperRGB** · `alpha[levelCount]` ·
  `offsets[frameCount+1]` · 各帧 zlib 流。**墨色/纸色/四档 alpha 都在文件头里**，
  不在 C++ 另写一份。

## 三个坑（都写进了源码注释）

1. **`GZIPDecompressorInputStream(InputStream&)` 默认是 zlib 不是 gzip**
   （`juce_GZIPDecompressorInputStream.cpp:142`，`format (zlibFormat)`）。
   喂 gzip 数据进去**一句错都不报、直接解不出来**。Python 侧必须用 `zlib.compress`。
2. **PNG 解码 8–14 ms/帧** → 15fps 就是单核 16–21%，而且每 66 ms 在 UI 线程卡一下。
   自打包后解码 **0.39–0.64 ms**。
3. **`Graphics::drawImage` 一旦要缩放就走双线性**（`juce_RenderingHelpers.h:1247`
   起是"读四个源像素再平均"），544→1088 实测重烤 4.56 ms。
   `setImageResamplingQuality(Graphics::lowResamplingQuality)` 退化成单像素读写
   （同文件 1098 行把双线性权重给 0）→ **3.35 ms**。对硬边字符画来说最近邻
   反而更好看（整数倍放大 = 精确像素复制）。

## 实测性能（1088×1976 @2x，Release）

- 背景重烤（解一帧 + 全幅贴图 + 树线，只在帧号变化时发生）**2.5–4.5 ms / 次**
