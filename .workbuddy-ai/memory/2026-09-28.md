### 教训：本机跑通 ≠ 全新克隆跑通

改 `run_tests.sh` 时我「优化」掉了原来的 `export PATH="...venv/bin:$PATH"`，
改成只把 ninja 路径通过 `-DCMAKE_MAKE_PROGRAM` 传给 cmake。本机有 `build/`
缓存，跑起来一切正常；**全新克隆从零构建就炸了**：

```
CMake Error: CMake was unable to find a build program corresponding to "Ninja".
ninja: build stopped: subcommand failed.
```

根因：JUCE 生成 VST3 manifest helper 时会**另起一个 cmake 子进程**配置
`external/JUCE/extras/Build/CMake/juce_v3_helper`，子进程**不继承**
`CMAKE_MAKE_PROGRAM`，只去 PATH 上找 ninja。外层只看到最后一句，
真正的错误在子进程里，非常难查。改回把 cmake / ninja 所在目录加进 PATH。

**推论：构建脚本的任何改动，都必须在 `/tmp` 里 clone 一份从零验证。**
已有 `build/` 目录会掩盖这类问题。这条已写进 `juce-vst3-plugin-dev` 技能。

另一个坑：构建的后处理会把产物拷进 `~/Library/Audio/Plug-Ins/`，沙箱会拦下
其中几个文件，命令返回非零 —— **但测试其实全过了**。判断结果要看日志里的
`passed` / `结论`，不要只看退出码。同类假失败还有 `gh auth login` 的 keychain 报错。

### README 数值核查：别把两个来源的数字混在一张表里

写 README 时凭印象把 Freeze 的实测值写成「自相关 0.9325」。逐条核对代码后发现：
那张表里其余五行（Stutter / Tape / Comb / Wavefold）全部来自**离线段探针**，
只有 Freeze 这行引的是**端到端验收**的数 —— 来源不一致，而且引的是偏低的那个。

实测离线段（6 种循环长度 20–1000 ms）：

```
loop_ms      自相关      周期误差    内容相关
     20   1.000003          0    1.000000
     50   0.999994          0    1.000000
    100   1.000005          0    1.000000
    250   0.999993          0    1.000000
    500   1.000061          0    1.000000
   1000   1.000295          0    1.000000
```

端到端只有 0.9325，是因为那条路径上 `Space Mix = 1`，混响混在信号里本身
就会去相关 —— **不是 Freeze 变差了**。两个数回答的不是同一个问题，
已在表格下加注。

**推论：README 里的每个数字都要能追到断言或探针输出，并且标明来源。**
一张表里混用不同来源，等于把两件不同的事说成一件。

其余引用也已逐条核对过出处：停转修复前 RMS `0.174`（test_deconstruct_dsp.py:132）、
限制器过冲 `+4.8dB → 峰值 1.0062`（test_engine_dsp.py:219）、
面板 `860×438`、48 参数（+1 Bypass = 49）、82 项测试、10 项 UI 防线。
